# GitHub and Paper Publication Guide

This guide separates software publication from scientific-result publication.
The repository can be public even when recordings, derived outputs, or models
must remain restricted.

## 1. Prepare the Repository

Before merging the publication branch:

```bash
python3 -m pytest -q
cd docs
python3 -m sphinx -E -W -b html source build/html
```

Review the public tree for local paths, credentials, temporary files, data, and
generated results:

```bash
git status --short
git diff --check
git grep -n '/Users/\|/data/' -- ':!docs/PUBLICATION_GUIDE.md'
```

Confirm that the README, license, citation, changelog, security policy,
contributing guide, package version, and documentation version agree. Replace
or extend the `CITATION.cff` author list before release if the software has
additional contributors who meet the project's authorship policy.

## 2. Create the GitHub Release

1. Merge the reviewed branch into the release branch.
2. Create an annotated tag such as `v1.0.0`.
3. Push the tag and create a GitHub release from it.
4. Use the corresponding `CHANGELOG.md` section as the release notes.
5. Attach the reviewed PDF manual and a SHA-256 checksum.
6. Confirm that the GitHub Pages workflow publishes the Sphinx documentation.
7. Archive the release in Zenodo or an equivalent repository if a DOI is
   required, then add the DOI to `CITATION.cff` in the next patch release.

Do not attach restricted recordings or identifiable data to a public release.
Trained models should be public only when their training-data governance,
license, intended use, limitations, and misuse risks permit distribution.

## 3. Archive a Scientific Analysis

For every reported experiment, archive:

- the release tag and exact commit hash;
- operating system, Python version, and locked package environment;
- input manifest and checksums;
- non-sensitive labels and their data dictionary;
- exact commands and random seeds;
- standard output/error logs;
- parameter CSV/JSON files generated by the pipelines;
- quality-control and missing-recording tables;
- fold-level metrics and held-out predictions;
- final figures and the code used to generate them;
- model metadata and manifests when models are reported.

Large outputs should be deposited in a data repository and linked from the
paper, not committed to Git. The repository intentionally ignores data,
outputs, figures, PDFs, and model binaries.

## 4. Manuscript Methods

Use `METHODS.md` or the printable manual as the starting point, then replace
defaults with actual run values. A complete methods section should state:

- recording count, biological-unit count, cultures, conditions, DIV range, and
  repeated-measurement structure;
- acquisition hardware, plate/grid geometry, sampling rate, duration, well,
  voltage scale, and reference channel;
- signal filters, detector threshold, waveform length, and polarity labels;
- plausible-negative and active-channel criteria with filter-stage counts;
- burst definition and all reported metric units;
- stratification scope, sampling, whitening, PCA variance, distance, candidate
  cluster counts, and cluster-selection method;
- supervised sample unit, features, algorithms, grouping, folds, repeats,
  leakage controls, model ranking, and metrics;
- connectivity bin/window sizes, thresholds, sign handling, map selection, and
  sensitivity analysis;
- software version, commit hash, dependency environment, and random seeds.

## 5. Manuscript Results

Results should report denominators before percentages. Include the number of
recordings and biological units per class or DIV value, spikes before and after
each filter, active channels, sampled waveforms, and missing recordings.

For classification, report the dummy baseline, fold-level variability,
balanced accuracy, accuracy, per-class recall/F1, confusion matrices, and the
absence or presence of independent external validation. For regression, report
MAE/RMSE in days, target range, baseline comparison, calibration plots, and
within-day tolerances. For connectivity, report edge density and parameter
sensitivity, not only the strongest-edge maps.

Avoid treating spikes from the same recording as independent supervised
samples, treating cross-validation folds as an external test cohort, comparing
cluster IDs from independently fitted models as if they were fixed biological
types, or selecting connectivity parameters only after inspecting the desired
result.

## 6. Figures and Tables

- Use vector formats for diagrams and plots when supported by the journal.
- Keep raster sensor maps at least 300 dpi at final printed size.
- Use readable legends outside dense plotting regions.
- Define colour scales and whether edge magnitude or sign controls selection.
- Include uncertainty and sample size in captions.
- Make cluster IDs explicitly analysis-specific.
- Provide source CSV tables for every summary figure when governance allows.

## 7. Citation and Availability Statements

The software statement should identify the repository URL, version, commit, MIT
license, and archived DOI when available. The data statement should describe
whether raw and processed recordings are public, controlled-access, available
on request, or unavailable for a stated governance reason. The model statement
should separately identify model files, metadata, training-data provenance,
license, and validation scope.

Suggested software availability text:

> Analyses were performed with 3D-BrAIn version [version], commit [hash]. Source
> code is available under the MIT License at
> https://github.com/cristinacampi/3D-BrAIn_codes. The archived release is
> available at [DOI].

## 8. Items Requiring Author Confirmation

Before the first public release, confirm the definitive software author list,
institutional acknowledgements, funding and grant numbers, preferred contact,
release version/date, archival DOI, dataset-access statement, and whether any
trained model can be distributed publicly. These are scientific and governance
decisions and should not be inferred from the codebase.
